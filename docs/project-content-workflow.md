# Project content workflow

Project cards and detail pages are driven by Astro's `projects` content collection. The source files live in `src/content/projects/`; the validated schema lives in `src/content.config.ts`.

Use this workflow to add a project, edit an existing project, preview it locally, and publish it without hand-editing generated HTML.

## Choose the content type

- **Migrated detail page:** Use [the detail-page template](templates/project-detail.mdx). Astro generates `/<routeKey>.html`. Set `listingOrder` below `999` to show the project on `/projects.html` and include it in generated detail-page navigation.
- **Listing-only entry:** Use [the listing-only template](templates/project-listing-only.mdx) only when the card points to an existing legacy root HTML file or an external URL. Astro does not generate a detail page for this entry.
- Use `.mdx` when the body uses the shared Astro components. Plain Markdown syntax works inside MDX.

## Add a project

1. Keep implementation based on and destined for `dev`, the repository integration branch. Work directly on `dev` when instructed, or create a ticket-scoped branch from `dev` and target `dev` with the pull request. Never base project-content work on production `master`.
2. If the project has local media, place it under `project/<routeKey>/`. Use root-relative-to-the-site paths without a leading slash in frontmatter and components, for example `project/new-project/hero.jpg`.
3. Copy the appropriate template into `src/content/projects/<routeKey>.mdx`.
4. Replace every template value. Keep `routeKey`, `route`, and `legacySource` aligned exactly as described below.
5. For a migrated detail page, add `/<routeKey>.html` to `astroManagedProjectRoutes` in `config/legacy-routes.mjs`. The post-build copy step uses this registry to normalize Astro's generated `<routeKey>.html.html` file to `dist/<routeKey>.html`.
6. Add the route key to `migratedProjectEntries` and update `expectedDetailNavigation` in `scripts/verify-jcr58-structured-project-details.mjs`. This keeps the MDX-authoring and generated-navigation regression checks complete.
7. Write the body in Markdown/MDX. Import only the shared project components the page uses.
8. If the project appears on `/projects.html`, update the legacy listing parity baseline as described below.
9. Run the local preview and inspect both `/projects.html` and the project route.
10. Run the complete verification gate before opening a pull request.

Do not add previous/next links to the MDX body. Detail navigation is generated from listing-visible collection entries (`listingOrder < 999`).

## Edit a project

1. Find the existing entry in `src/content/projects/`.
2. Edit frontmatter for listing, social-card, date, or ordering changes. Edit the MDX body for project-page content.
3. Put new media in the existing `project/<routeKey>/` directory and provide meaningful `alt` text.
4. If listing metadata changes, update the matching card in the legacy listing parity baseline described below.
5. Treat a `routeKey` change as a URL migration: update `route`, `legacySource`, the route registries and navigation expectations named above, asset references, and inbound links together. Avoid changing a published route unless the redirect and compatibility impact is intentional.
6. Preview and verify using the same checks as a new project.

Never edit `dist/`. It is generated by the build and ignored by Git.

## Maintain the legacy listing parity baseline

`scripts/verify-jcr45-project-parity.mjs` compares cards generated from the content collection with the visible project cards in the root `projects.html`. That root file is retained as a migration baseline even though Astro owns the built `/projects.html` route.

Whenever a project has `listingOrder < 999`, add or update its corresponding card in the root `projects.html` so its link, image, alt text, title, subtitle, and ordering match the MDX frontmatter. Do not edit `dist/projects.html`; the build recreates it. The parity check fails intentionally when the collection and legacy baseline drift.

## Frontmatter schema

The build validates these fields through `src/content.config.ts`.

| Field | Requirement | Meaning and constraints |
| --- | --- | --- |
| `title` | Required | Project title, 1 to 120 characters. |
| `titleSuffix` | Optional | Browser/social title suffix, 1 to 120 characters. Defaults to `title`. |
| `routeKey` | Required | Lowercase letters, numbers, and hyphens only. |
| `route` | Required | Must be exactly `/<routeKey>.html`. |
| `legacySource` | Required | Must be exactly `<routeKey>.html`. |
| `year` | Optional | Integer from 2000 through 2100. |
| `detailDate` | Required for `migrated` | Display text shown above generated detail navigation, 4 to 40 characters. |
| `featured` | Optional | Boolean; defaults to `false`. Reserved project metadata. |
| `listingTitle` | Optional | Card title, 1 to 120 characters. Defaults to `title`. |
| `listingSubtitle` | Required when listed | Comma-separated card labels, 1 to 160 characters total. Use three to five short, reusable disciplines or technology categories. Required when `listingOrder < 999`. |
| `listingImage` | Required when listed | Card image path, 1 to 300 characters. Required when `listingOrder < 999`. |
| `listingImageAlt` | Optional | Card image alternative text, 1 to 120 characters. Requires `listingImage`. |
| `listingHref` | Optional | Card target: `<name>.html`, `/<name>.html`, or an absolute HTTP(S) URL. Defaults to `route` without its leading slash. |
| `listingOrder` | Optional | Integer from 0 through 999; defaults to `999`. Values below `999` appear on `/projects.html` and participate in previous/next navigation; ties are ordered by `routeKey`. |
| `detailNavOrder` | Required for `migrated` | Integer from 0 through 999. Omit it for `legacy-wrapped` entries. This remains schema-required metadata, but the current listed-project navigation follows `listingOrder`; keep the values aligned unless a follow-up changes navigation behavior. |
| `tags` | Optional | Up to 12 unique values, each 1 to 32 characters; defaults to `[]`. |
| `status` | Required | `migrated` generates a detail page. `legacy-wrapped` is metadata/listing-only and must not define `detailNavOrder`. |
| `summary` | Required | General description, 10 to 220 characters. |
| `socialImage` | Optional | Social preview image URL or path, up to 400 characters. Prefer an absolute production URL. |
| `socialDescription` | Optional | Social preview description, 10 to 220 characters. |
| `socialCard` | Optional | `summary` or `summary_large_image`; defaults to `summary_large_image`. |
| `includeCocoenAssets` | Optional | Boolean; defaults to `false`. Enable only when the page uses the bundled Cocoen comparison assets. |

The build also rejects duplicate routes across page and project collections. It is the final authority if this guide and the schema ever diverge.

### Project-card label convention

Treat `listingSubtitle` as a compact taxonomy, not a second description. Use three to five comma-separated labels that a reader can scan and that can be reused across projects, such as `Edge AI`, `Embedded Systems`, or `3D Printing`. Keep narrative claims, project milestones, model or device part numbers, and low-level package inventories in `summary`, `tags`, or the detail-page content instead.

## Shared MDX components

Components live in `src/components/project-details/`. Existing project entries are the best reference for more elaborate compositions.

| Component | Main props | Use |
| --- | --- | --- |
| `ProjectHero` | `title`, `tagline`, `mediaType`, `mediaSrc`, optional `mediaAlt`, `links` | Standard project introduction with an image or embed. Link icons are `github` or `globe`. |
| `ProjectSection` | optional `heading`, `border`, `wide`, `className` | General content section. |
| `ProjectSplitSection` | `heading`, `lead`, optional `border` | Lead statement beside body content. |
| `ProjectImage` | `src`, optional `alt`, `shadow`, `centered` | Single image. |
| `ProjectVideo` | `src`, optional `wide`, `spacingAfter` | Embedded video. |
| `ProjectMediaPair` | `heading`, `imageSrc`, optional `imageAlt`, `reverse`, `border` | Image and prose pair. |
| `ProjectCarousel` | `items`, optional `variant` | Carousel; variants are `side`, `full`, and `gallery`. |
| `ProjectCarouselSection` | `heading`, `items`, optional `variant`, `border`, `wide` | Carousel in a complete section. |
| `ProjectCards` / `ProjectCard` | wrapper; card uses `title`, `imageSrc`, optional `imageAlt` | Grouped project cards. |
| `ProjectColumns` | optional `heading`, `wide` | Multi-column content wrapper. |
| `ProjectFeature` | `icon`, `title` | Icon-led feature item. |
| `ProjectLinks` | `links` | Text links with `href` and `label`. |
| `ProjectTheoryCard` | `title`, `imageSrc`, optional `imageAlt` | Theory/reference card. |

## Local preview

The repository uses the Node version in `.nvmrc` (currently Node 22).

```bash
nvm use
npm ci
npm run dev
```

Open the URL Astro prints, normally <http://localhost:4321/>. Check:

- `/projects.html` contains the card in the expected position and its link works.
- The generated project route renders all content and media without console errors.
- Previous/next navigation follows the listed-project sequence from `listingOrder`.
- Desktop and mobile layouts remain usable.
- External links and embedded media load correctly.

Before submitting, run the same full gate used by CI:

```bash
npm run verify:ci
```

This builds the static site, copies retained legacy assets, runs migration/parity checks, and verifies internal links.

## Publish path

1. Push the ticket-scoped branch and open a pull request targeting `dev`.
2. The `Verify` GitHub Actions workflow runs `npm ci` and `npm run verify:ci` for pull requests into `dev`.
3. After review, merge into `dev` only when authorized. Do not merge a contributor branch directly to production.
4. Production releases use a separate `dev` to `master` pull request and the repository release gate.
5. A push to `master` triggers the production `Deploy to GitHub Pages` workflow. It reruns `npm run verify:ci`, uploads `dist/`, and deploys through the `github-pages` environment.
6. Confirm the Actions run is green and smoke-test the live project URL and `/projects.html`.

The deploy workflow currently lives on the production branch: [`.github/workflows/deploy-pages.yml`](https://github.com/jasontsemf/jasontsemf.github.io/blob/master/.github/workflows/deploy-pages.yml).

## Submission checklist

- [ ] Frontmatter satisfies the schema and route-derived values match.
- [ ] Each migrated route is registered in `astroManagedProjectRoutes` and covered by the structured-project verifier.
- [ ] Each listing-visible project matches its card in the root `projects.html` parity baseline.
- [ ] Listing and detail navigation order are intentional.
- [ ] Images and embeds load; meaningful alt text is present.
- [ ] `/projects.html` and the detail or legacy target were previewed locally.
- [ ] `npm run verify:ci` passes.
- [ ] The pull request targets `dev`, links its ticket, and lists affected routes.
- [ ] CI passes before merge or release.
